## The problem, in the owner's words

Tielora's customers live in Teams all day. Today, to see what needs them, they leave Teams, open a browser and sign in. The owner wants Tielora to be one click inside the tool the company already has open: a "Tielora" icon in Teams that shows "your day" right there. Channel notifications already work through the Teams webhook a company pastes in Admin → Integrations, and they stay exactly as they are.

## What changes for the user (plain English)

1. **A company's Teams admin (or any person, for a pilot) can add Tielora to Teams.** Tielora's own administrator downloads a small package from Admin → Integrations and follows a short, plain-English "how to add it" note on the same card.
2. **A "Tielora" app in Teams with one tab, "Your day".** It shows the same brief as Tielora's own "Your day" page — due today, overdue, newly unblocked, mentions, awaiting your review, announcements — for the signed-in person, inside Teams.
3. **No second login for most people.** If the person has signed in with Microsoft to Tielora before, the tab opens straight to their day. If not, the tab says "Sign in to see your day" with one button; a small Microsoft window opens, they approve once, and the tab fills in. Anyone with two-factor on is still asked for their six digits.
4. **Read-only, on purpose.** The tab shows the day and links out. Every link opens Tielora in the browser (Teams' "open link"), where the person does the work. Nothing can be changed from the tab.
5. **Nothing switches on by itself.** Until the owner sets one setting on the deployment, none of this exists: no card, no package, no tab page, nothing different for anyone.

## Screen by screen

**A. Admin → Integrations, new card "Microsoft Teams app"** (below the existing Microsoft Teams chat card and the Microsoft 365 card; shown to an ADMIN only, and **not shown at all while the deployment has not set the app up**).
- One-line explanation: "Put Tielora inside Teams. Your people get a 'Your day' tab in the Teams sidebar. Channel messages are set up separately, in the Teams card above, and are not changed by this."
- Button **Download Tielora for Teams** — saves `tielora-teams-app.zip`. Helper line: "This file is the same for everyone at your company. It contains no passwords or secrets."
- Plain-English "How to add it" (collapsed by default, opens on a click), two routes:
  - *Just to try it (only for you):* In Teams choose Apps → Manage your apps → Upload an app → Upload a custom app, and pick the file. If you do not see "Upload a custom app", your Teams administrator has switched that off; use the second route.
  - *For everybody at your company:* Your Teams administrator opens the Teams admin centre → Teams apps → Manage apps → Upload new app, picks the file, then (optional) adds it to a Setup policy so it appears pinned for everyone.
  - *First time in the tab:* each person may see a Microsoft "approve" prompt once. If it says "needs admin approval", your Microsoft administrator approves Tielora once for the company (the owner has the link in GO-LIVE).
- If this company has not yet linked its Microsoft work account (the Microsoft-first step), a notice above the button: "People cannot sign in inside Teams until your Microsoft work account is linked. Do that in the Microsoft 365 card above first." The button still works; the package is harmless without it.
- Hover hints on the button and each collapsed step per the house hint rule; keyboard-reachable.

**B. Inside Teams — the tab (`/teams/tab`).** Three states.
1. *Signed in.* Title "Your day" (no sidebar, no top bar, no footer — Teams already supplies the frame). Below, the same sections and wording as Tielora's "Your day" page, each capped at 10 with its true total, same as today. Each row is a plain button that opens its Tielora page in the browser. A small line at the bottom: "Open Tielora in your browser" (a link to `/my-tasks/brief`). No forms, no buttons that change anything, no sign-out (the person is signed in to Teams; leaving Tielora's browser session is unaffected).
2. *Not signed in.* A centred card: "Sign in to see your day", one line "Use your work Microsoft account.", one button **Sign in with Microsoft**. Pressing it opens the Microsoft window. If it fails the card says only "We could not sign you in with Microsoft. Ask your Tielora administrator if this keeps happening." — the same sentence whatever the reason (company not switched on, no matching account, deactivated, access expired). Nobody learns which.
3. *Two-factor.* After Microsoft accepts them, if their Tielora account has two-factor on, the card asks for "the 6-digit code from your authenticator app" (or a recovery code, exactly like the sign-in page: same wording, same one-sentence failure). Only after a good code does the tab fill in.
4. *Blocked cookies fallback.* If the browser or Teams mobile will not keep the tab's sign-in (third-party storage blocked), the tab shows "Your browser is blocking Tielora inside Teams. Open Tielora in your browser instead." with an **Open Tielora** button. No dead spinner, no error jargon.
- Loading: a skeleton of the section rows (house skeleton rule). Empty day: the same "nothing needs you today" wording the page already uses.
- Right-to-left / Arabic: Tielora is English-only (house rule 6); nothing bilingual here. Use logical start/end spacing anyway so a later Arabic pass costs nothing.
- **Run `ui-designer` before building** (the three states, the narrow phone-in-Teams width, dark mode — Teams passes its theme and Tielora may follow it with brand tokens only, and the package icons).

**C. The Microsoft window (popup).** Opened by Teams' own sign-in window API. It is the ordinary Microsoft sign-in from the Microsoft-first spec, told it was started from Teams. It closes itself when done. There is no screen of ours in it except a one-second "Signing you in…" page.

## Who can use it — including contractors

Everyone with a Tielora account who can sign in: administrators, project managers, engineers and **EXTERNAL contractors (decision: yes)**. The tab shows exactly what that person's own "Your day" shows today and nothing more, because it is built from the very same function that page uses (`personBrief(actor)`), not a second query. For a contractor that means: their own tasks, and the opt-in "Notices" lines (title, body, poster, date, with no link because there is no page they may open). No team roster, no other person's task, no project they hold no work on, no noticeboard. Their row links go only to discipline-task pages they already may open. Contractor expiry and deactivation are checked by the same session layer, so an expired contractor sees the sign-in state and the same generic failure.

## What is explicitly OUT of scope

- **The bot** and one-to-one Teams messages (named follow-up, next round). **No new table this round** — there is no `teams_installations` table and no Prisma migration in this build.
- **Activity-feed ("bell") notifications**, adaptive-card actions inside Teams, message extensions, meeting apps.
- **A channel tab** pointing at one project (later follow-up).
- **A Teams Store listing** and its review (needs the privacy, terms and support pages checked; later). Sideload and a customer's own catalogue only.
- **Changing notifications.** The existing per-company webhook, its toggles, the daily digest and the weekly brief are untouched.
- **Anything editable in the tab**: no marking done, no comments, no acknowledging, no password form. (Acknowledge stays in the browser; the tab's "waiting for your acknowledgement" line links there.)
- **A password sign-in form inside Teams.** People without a Microsoft link use the popup or open the browser.
- **Government / China Microsoft clouds** (their Teams hosts are different).
- **In-memory session fallback for browsers that block the tab cookie** (see open question 1).

## The security changes — read this part twice

1. **Framing is allowed for exactly one page.** Today every page carries `frame-ancestors 'none'` and `X-Frame-Options: DENY`. After this build, **only `/teams/tab`** answers with `frame-ancestors 'self'` plus an explicit list of Microsoft Teams hosts, and **no** `X-Frame-Options` on that one response. Every other page and every API route is unchanged, byte for byte. Never a bare `*`, never `https:`. The builder confirms the current host list on Microsoft Learn before coding (the research flagged it unverified): the working starting list is `https://teams.microsoft.com https://*.teams.microsoft.com https://*.office.com https://*.microsoft365.com https://outlook.office.com https://*.cloud.microsoft`. The Microsoft popup pages are not framed and stay DENY.
   - Why this is acceptable: the framable page is read-only and holds no form of any kind that changes data, so clicking through a hidden frame achieves nothing.
   - How to build it so it cannot leak: the config becomes two header rules — the existing global one, rewritten to **exclude** `/teams/tab`, and a second one for `/teams/tab` alone. The rest of the CSP (script, connect, frame-src, form-action…) is identical on both; only the framing pair differs, from one shared function so they cannot drift.
   - The framing permission is in the build's headers even when the app is dormant; while dormant the page answers "not found" (a framable "not found" page is harmless).
2. **The tab's sign-in cookie is different, and boxed in.** The normal `nexus_session` cookie stays `SameSite=Lax` and is never touched. The tab gets its **own cookie** (`tielora_teams`): `HttpOnly; Secure; SameSite=None; Partitioned; Path=/teams`.
   - `Partitioned` means the browser only sends it when Tielora is inside a Teams page (not from any other website), which is what blunts cross-site request forgery for a `SameSite=None` cookie.
   - `Path=/teams` means it is never sent to any `/api/...` route or any other page, so **no data-changing route can ever be reached with it**.
   - It is read in one place, a new `getTeamsTabUser()` next to `getSessionUser()`, and only by `/teams/tab`. `getSessionUser()` ignores it and the tab ignores `nexus_session`. Both cookies point at the same kind of `Session` row and share every check (person active, contractor access not expired, session not expired), and `revokeSessions()` — used on deactivation and expiry — kills the tab session with all the others. No new table.
   - Same 7-day life as a normal session.
3. **The Teams token is checked like a bank cheque.** Teams hands the tab a short-lived Microsoft-signed token (single sign-on). The server accepts it only after all of: signature verified against Microsoft's published signing keys; token not expired and not used before its start time; audience is exactly this deployment's app (the builder pins the ONE audience value the Azure registration really issues — the app's client id or its `api://<host>/<client id>` address — after inspecting a real token, and accepts nothing else); issuer is `https://login.microsoftonline.com/<tid>/v2.0` where `<tid>` is the token's own tenant id; the granted scope is `access_as_user`; the calling client is one of the two Teams client ids listed in the research; `tid` and `oid` are present; only the signing algorithm Microsoft uses (RS256) is accepted — "none" and any shared-secret algorithm are refused. Anything else fails closed with the generic sign-in failure.
   - **Identity is `tid` + `oid` only.** The token has no reliable verified email, so the tab **never** matches on email. A person whose `oid` is not yet pinned goes through the popup path, which is the Microsoft-first sign-in (where the verified-email first-link rule lives) and pins the `oid`.
   - The signing keys are fetched from Microsoft's key address (host `login.microsoftonline.com`, already on the outbound allow-list in `ms-graph.ts`), cached in memory for up to an hour, and an unknown key id triggers at most one re-fetch per minute so garbage tokens cannot make Tielora hammer Microsoft. If Microsoft cannot be reached, sign-in fails closed. The validator is the Microsoft-first spec's validator with a second "audience profile", not a second copy.
4. **Two-factor is still asked.** Nothing about Microsoft's own two-factor replaces Tielora's. With Tielora two-factor on, the token/popup step only produces the same five-minute pending ticket (`TWOFA_PENDING`) the password sign-in produces; no session and no cookie exist until a good code arrives. The tab's code step is `POST /api/teams/two-factor`, a thin twin of `/api/auth/two-factor`: **one shared implementation, the route decides which cookie to set — never a field in the request body**. It shares the same ticket budget (5 tries) and the same per-account budget (8 per 15 minutes) as the browser route, so the tab is not a second, free place to guess codes.
5. **One-time hand-off for the popup.** The popup runs in its own browser jar, so it cannot set the tab's cookie. When the Microsoft-first callback is started from Teams it does **not** create a session; after the identity rule passes it mints a single-use, two-minute **hand-off code** (an `EmailToken` row with a new plain-string purpose `TEAMS_HANDOFF`, hash only, never emailed — the same shape and the same "never in `EmailedPurposeName`" rule `TWOFA_PENDING` follows; **no migration**, the purpose is validated by zod) and redirects the popup to `/teams/auth-end`, which hands the code to the tab and closes. The tab exchanges it at `/api/teams/session` (single use, conditional update). Accepted limit: the code travels between two Teams windows for at most two minutes; it is worthless once used and cannot bypass the two-factor step, which happens after the exchange.

## Routes added or changed

| Route | What it does |
|---|---|
| `GET /api/teams/manifest` | The zip download. ADMIN of the caller's own company (`MANAGE_INTEGRATIONS`, `can` then `assertCan`). The zip is the same for every company, so the tenant rule has nothing to leak, but the door is still shut to anyone else: a non-admin, a contractor and a signed-out caller all get "not found". Dormant: "not found" too. `byUser` limited, 10 a minute. Returns `Content-Disposition: attachment`, `Cache-Control: private, no-store`. Writes no audit row (nothing changes; a download is not project work and reveals no secret). |
| `POST /api/teams/session` | Body: exactly one of `{ ssoToken }` or `{ handoffCode }`. Success without two-factor: sets the tab cookie, appends the `LOGIN` row, returns `{ status: "SIGNED_IN" }`. With two-factor: `{ status: "TWO_FACTOR_REQUIRED", pendingToken, expiresAt }` and nothing else happens. Any failure: 401 with the one generic sentence. Public. |
| `POST /api/teams/two-factor` | The second step, described above. Same body and same answers as `/api/auth/two-factor`, but sets the tab cookie. |
| `/teams/tab` (page) | The tab. Dormant: not found. Not signed in: the sign-in state. Reads only. |
| `/teams/auth-end` (page) | The popup's last stop. Not framable. Reads the hand-off code from the address fragment (never sent to the server), passes it to the tab, closes. |
| `GET /api/health` | Adds `"teams_app": "dormant" \| "configured"` — a word and nothing else, for signed-in callers like the rest of the detailed body. |
| `/api/auth/microsoft` | Microsoft-first's route, with the "started from Teams" mode described below. |

## Setting it up on the deployment (dormant until set)

- New env var **`TEAMS_APP_ID`**: a GUID the owner generates once (any GUID; it identifies the Teams app, not a secret). `"configured"` means **all of**: `TEAMS_APP_ID` is a valid GUID, `APP_BASE_URL` is an https address, and the Microsoft app registration is set (`MS_GRAPH_CLIENT_ID` and `MS_GRAPH_CLIENT_SECRET`, already used by Microsoft-first). Anything missing is `"dormant"`, and dormant means: no admin card, `/api/teams/manifest` and the tab page say "not found", `/api/teams/session` and `/api/teams/two-factor` answer "not set up" (503), and nothing else in the app looks or behaves differently. Follows house rule 11.
- **The package** is built in code (a typed manifest in `src/lib/teams-manifest.ts`, not a static file, so the host and ids can never be stale), zipped with the repo's existing `src/lib/zip.ts`, and contains `manifest.json`, `color.png` (192×192) and `outline.png` (32×32) read from **`public/teams/`**. The manifest holds, per deployment: `id` = `TEAMS_APP_ID`; the schema version the Teams Developer Portal currently validates (builder checks on Learn — do not guess); a `version` constant that is bumped whenever the manifest changes; name "Tielora"; short description in plain English; `developer` block with `APP_BASE_URL`, `/privacy` and `/terms`; a `staticTabs` entry (entity id `your-day`, name "Your day", content address `<APP_BASE_URL>/teams/tab`, scope personal); `validDomains` = this deployment's host only; `webApplicationInfo` with the client id and `api://<host>/<client id>`; the accent colour is the existing `--brand-primary` value copied once with a comment saying so (house rule 7 — not a new colour). Nothing about any company is in it.
- The icons are designed by `ui-designer` from the existing Tielora mark (colour version on the brand background, outline version single-colour transparent, as Teams requires).

## Coordination with Microsoft first (the two things this spec asks of it)

1. **A "started from Teams" mode on `/api/auth/microsoft`** (for example `?via=teams`), whose callback, after the ordinary identity rule and pinning, mints the hand-off code and redirects to `/teams/auth-end` instead of creating a session and setting `nexus_session`. Every other behaviour and every failure sentence is identical. The mode is a fixed flag that only changes the ending; it cannot loosen any check.
2. **The token validator is exported and takes an audience profile**, so the sign-in ID token and the Teams SSO token are checked by the same code.
If Microsoft-first is built without these, this build adds them; the rule is one identity path, never two.

## The data touched (plain terms)

- **Nothing new is stored about anyone.** No new table, no new column, no migration. A tab sign-in adds one ordinary sign-in record (the same kind a browser sign-in adds), stamps "last signed in" on the person, and adds one audit line.
- The single-use hand-off code is a short-lived row in the existing email-token table (hash only, deleted with the person like the others). It carries no personal data beyond "this person's Microsoft identity was accepted a moment ago".
- The person's Microsoft ids (`tid`, `oid`) are already pinned by the Microsoft-first spec; this build only reads them.
- The signing-key cache is in memory only.

## Standards note (engineering-standards sections 6–8)

- **New personal data collected?** No. The tab reads data the app already holds and stores nothing about anyone that Microsoft-first does not already store. So no privacy-page change is *required by this build*. **Recommendation, one sentence, same change:** the privacy page has no sentence about the sign-in cookie today (I searched it for "cookie"); add one plain sentence — "Inside Microsoft Teams, Tielora uses a separate sign-in cookie that only works within Teams" — so the page is true to the code. Microsoft-first owns the bigger "Microsoft as a processor / your Microsoft ids" text; this build does not duplicate it.
- **Touches a core guarantee?** Not the golden rule or the stage gate (nothing here writes a task, a document or an audit row about work). It **does** touch the tenant rule and the external rule, so tests are mandatory in `org-isolation.service.test.ts` and `external-scoping.service.test.ts` (below).
- **Adds mutations / external calls?** Yes — three write-capable public routes and one outbound fetch. Rate limiting, per house rule 10: `POST /api/teams/session` — `byIp` 20 a minute, plus failures-only counting on the hand-off code (10 wrong per 15 minutes per address); `POST /api/teams/two-factor` — `byIp` 20 a minute plus the **existing** ticket and account budgets, shared, not new ones; `GET /api/teams/manifest` — `byUser` 10 a minute. All deny with 429, a plain-English message and `Retry-After`. The one outbound call is Microsoft's public signing-key fetch (host already allow-listed, cached, re-fetch capped as above); no other new host, and `@microsoft/teams-js` is bundled from npm — never a CDN, which the CSP would block anyway.
- **Backups:** nothing new to back up.

## AUDITED

Every tab sign-in writes **the same `LOGIN` row** in the same transaction that creates the session and stamps `lastLoginAt` — no session without the row, no row without the session — exactly as `/api/auth/login` and `/api/auth/two-factor` do. Its metadata adds `via: "teams-sso"` or `via: "teams-popup"` next to the existing reported-IP and two-factor fields. A refused sign-in writes no row (as today). Reading the tab writes nothing (like the brief). Downloading the package writes nothing. The first-time link of an `oid` is audited however Microsoft-first audits it; this build adds no separate rule.

## Tests (all in the same change; none touches the network — `global.fetch` is mocked)

1. **No other route gained a frame permission** (`src/server/__tests__/security-headers.test.ts`, new). Load `next.config.ts`'s `headers()`; assert (a) exactly one rule permits framing and its source is exactly `/teams/tab`; (b) the general rule's source excludes only that path; (c) walking every `page.tsx` and `route.ts` under `src/app`, resolve each route's URL and assert every one **except `/teams/tab`** resolves to `frame-ancestors 'none'` and `X-Frame-Options: DENY`, including `/teams/auth-end`, `/login`, `/api/health`, `/api/teams/manifest`, `/api/teams/session`; (d) the permissive list contains no bare `*`, no `https:` and no `http:` entries; (e) everything else in the CSP is identical between the two rules. This test fails loudly if anyone adds a second framable route.
2. **Token validation** (`src/server/__tests__/teams-token.test.ts`, new; the test generates its own RSA key pair, serves the public key from the mocked key fetch, and signs test tokens). Accepts a good token. Refuses: expired; not yet valid; wrong audience; issuer whose tenant differs from the token's `tid`; wrong signature (a different key); unknown key id; `alg: none`; a shared-secret algorithm signed with the public key (algorithm-confusion attack); missing `access_as_user` scope; an unknown calling client; missing `oid` or `tid`; a token with an `email` claim but no pinned `oid` (must not sign in — no email matching in the tab). Key fetch failing → refused, no exception leaks. Cache: a second validation does not refetch; ten unknown-key tokens in a minute cause at most one refetch. The fetch mock asserts the only host ever requested is `login.microsoftonline.com`.
3. **Organisation isolation** (extend `org-isolation.service.test.ts`). Two companies, two Microsoft tenants. A valid token from tenant B never yields a company-A person, even when its `oid` equals a company-A person's pinned `oid`; a valid token from a tenant no company owns is refused with the same answer; a hand-off code minted for a company-A person cannot be exchanged into a session for anyone else and is dead after one use; the manifest route is "not found" for a signed-out caller, for a non-admin, and for a contractor; the tab page read is scoped by the session's own `orgId`.
4. **Contractor** (extend `external-scoping.service.test.ts`). A contractor signing in through the tab receives exactly the `personBrief` a contractor gets in the browser: only their assigned tasks; the opt-in Notices with an empty link; no roster; no other person's task. An expired or deactivated contractor is refused at token exchange and at the tab read with the generic answer.
5. **Cookie box**: a request carrying only `tielora_teams` to `/api/my-tasks/brief` (and to a data-changing route) is answered as signed-out; a request carrying only `nexus_session` to the tab page shows the sign-in state; the cookie set by the tab routes has `SameSite=None; Secure; Partitioned; HttpOnly; Path=/teams` and the browser routes still set `SameSite=Lax`.
6. **Sign-in chain**: password-only account → session + cookie + one `LOGIN` row with the `via` marker; two-factor account → no session, no cookie, no `LOGIN` row until a good code; a wrong code spends the shared budget and a fifth wrong try kills the ticket; a replayed code is refused; the tab and browser routes share one counter; rate-limit 429s carry `Retry-After`.
7. **Health / dormancy**: unset env → `"teams_app": "dormant"`, the card absent, manifest and tab "not found", session routes 503; all set → `"configured"`. The health test also asserts no id, host or secret appears in the value.
8. **Package**: the built manifest has the expected `id`, one `staticTabs` entry, `validDomains` equal to exactly one host (the deployment's), the `api://` resource matching the client id, https URLs only; the zip contains exactly three files and the icon files have the right pixel sizes.
9. Existing `mutation-safety.test.ts` keeps passing (this build must not add UPDATE or DELETE on `DocumentVersion` or `ActivityLog`).

## Open questions (max 3, each with my default)

1. **Phones and Safari may refuse the tab's sign-in cookie.** Teams on some phones and browsers block third-party storage even for `Partitioned` cookies. Should this round also build the fallback (a short-lived sign-in token held only in the tab's memory, so a phone still works)? **Default: no — ship with the plain "open Tielora in your browser" message, test on a real iPhone and Android in the sandbox tenant, and build the memory fallback only if the message shows up on modern current phones.** It is a bigger security surface than the cookie, so I would rather not build it speculatively.
2. **Do we keep the Teams-app card visible to administrators of a company that has not linked Microsoft yet?** **Default: yes, with the notice at the top of the card,** so the administrator learns what is missing instead of finding nothing.
3. **Which web address does the pilot use?** The package, the Azure "Application ID URI" and the redirect addresses all contain the site's address, so a later move to a custom domain means updating all three and re-uploading a new zip to every company. **Default: pilot on the current Railway address, and treat a domain change as a re-publish with a bumped package version (written up in GO-LIVE).** If a custom domain is planned within weeks, say so now and we start on it instead.
